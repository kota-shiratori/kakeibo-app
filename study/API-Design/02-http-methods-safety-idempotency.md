# HTTP メソッドと「安全性」「冪等性」

## 概要

HTTP メソッドには、HTTP の仕様（RFC 9110）で定められた 2 つの重要な性質があります。

- **安全（safe）**: そのリクエストでサーバーの状態が変わらない（読み取り専用）ことを意図したメソッド。
- **冪等（idempotent / べきとう）**: 同じリクエストを 1 回送っても N 回送っても、サーバーに与える **意図された効果** が同じになるメソッド。

| メソッド | 安全 | 冪等 | 主な用途 |
| --- | --- | --- | --- |
| GET | ○ | ○ | 取得 |
| HEAD | ○ | ○ | ヘッダーだけ取得 |
| OPTIONS | ○ | ○ | 対応メソッドの問い合わせ（CORS のプリフライトでも使う） |
| PUT | × | ○ | 丸ごと置き換え |
| DELETE | × | ○ | 削除 |
| POST | × | × | 作成・その他の処理 |
| PATCH | × | ×（仕様上は保証されない） | 部分更新 |

安全なメソッドは必ず冪等でもあります（何も変えないので、何度やっても同じ）。

## このプロジェクトでの実装

- `GET /transactions`（`backend/src/index.ts:18-49`）: 一覧を返すだけで、何も書き換えていません。**安全・冪等** の性質どおりです。
- `POST /transactions`（`backend/src/index.ts:51-84`）: 「収支を作成する」操作です。現状はまだ保存処理がなく受け取った値を返すだけですが（`backend/src/index.ts:83`）、本来の意味は **非冪等** です。データベースに保存するようになれば、2 回送ると 2 件登録されます。

フロントエンドでは、登録ボタンにローディング状態を渡しています。

`web-app/src/pages/Input.tsx:123-131`

```tsx
<Button
  type="submit"
  ...
  loading={isLoading}
>
  登録
</Button>
```

Chakra UI の `loading` が true の間はボタンが操作できない状態になるため、POST の二重送信をある程度防げます。POST が非冪等だからこそ、こうした対策に意味があります。

## 重要語句

- **安全（safe）**: リソースの状態を変えない。
- **冪等（idempotent）**: 何回繰り返しても結果（サーバー側の状態）が同じ。
- **二重送信**: ボタン連打や通信リトライで同じ POST が複数回届くこと。

## 仕様・注意点

- 冪等性は「レスポンスが毎回同じ」という意味ではありません。たとえば `DELETE /transactions/1` は 1 回目が `204`、2 回目が `404` になり得ますが、「ID=1 が存在しない」というサーバーの状態は同じなので冪等です。
- 「安全」はあくまで **意図** の話です。GET のハンドラ内でデータを書き換える実装も技術的には書けてしまいますが、ブラウザやプロキシ、クローラーは GET を気軽に送る・キャッシュする前提で動くため、絶対に避けます。
- 冪等なメソッドは、通信失敗時に自動リトライしても安全です。POST は自動リトライすると重複作成の危険があります。

## 今後に活かせるポイント

- 「このエンドポイントは何度呼ばれても大丈夫か？」を考える癖をつけると、メソッド選びやリトライ設計を間違えにくくなります。
- 取得系は必ず GET、状態を変えるものは GET 以外、が基本ルールです。

## 改善するなら

POST の重複作成をサーバー側で防ぎたい場合は、**冪等キー（Idempotency-Key）** パターンがあります。クライアントがリクエストごとに一意なキーを付け、サーバーは同じキーのリクエストを 2 回目以降は処理せず、前回の結果を返します（Stripe などの決済 API で有名）。

```ts
// クライアント側のイメージ
await fetch(`${BASE_URL}/transactions`, {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "Idempotency-Key": crypto.randomUUID(), // 1 回の「登録操作」ごとに 1 つ
  },
  body: JSON.stringify(transaction),
});
```

※ `Idempotency-Key` ヘッダーは IETF でドラフト段階の仕様です。採用する場合は CORS の `allowHeaders` にも追加が必要です（`backend/src/index.ts:13`）。
