# IDENTITY 列（自動採番）

## 概要

`id` のような連番は、アプリで数えるのではなく **DB に採番させる** のが基本です。PostgreSQL 10 以降は SQL 標準の **IDENTITY 列** が使え、現在はこれが推奨の書き方です。

## このプロジェクトでの実装

```sql
id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
```

- `BIGINT`: 型（8 バイト整数）
- `GENERATED ALWAYS AS IDENTITY`: 値は **常に** DB が生成する
- `PRIMARY KEY`: 主キー（`../Database/02-keys-and-indexes.md`）

そのため INSERT では `id` を書きません。

```sql
INSERT INTO transactions (item, amount, date) VALUES ('おこづかい', 30000, '2025-10-01');
```

backend も同様で、採番された `id` は `RETURNING` で受け取っています（`backend/src/index.ts:93-96`、→ 06 章）。

## 重要語句

| 書き方 | 意味 |
| --- | --- |
| `GENERATED ALWAYS AS IDENTITY` | 常に自動採番。値を指定するとエラー |
| `GENERATED BY DEFAULT AS IDENTITY` | 値を省略したときだけ自動採番。指定すればその値が入る |
| `SERIAL` / `BIGSERIAL` | 古い書き方。実体は「シーケンス + `DEFAULT nextval(...)`」。今は IDENTITY が推奨 |
| シーケンス | 連番を発行する DB オブジェクト。IDENTITY 列も内部ではシーケンスを使う |
| `OVERRIDING SYSTEM VALUE` | `ALWAYS` の列に、例外的に値を指定して入れるための句 |

## 仕様・注意点

### `ALWAYS` の列に値を指定するとエラー（実験で確認）

```text
INSERT INTO transactions (id, item, amount, date) VALUES (100, 'x', 1, '2025-10-01');
ERROR:  cannot insert a non-DEFAULT value into column "id"
DETAIL:  Column "id" is an identity column defined as GENERATED ALWAYS.
HINT:  Use OVERRIDING SYSTEM VALUE to override.
```

HINT の通りにすると入ります（データ移行などの特殊な場面用）。

```text
INSERT INTO transactions (id, item, amount, date) OVERRIDING SYSTEM VALUE VALUES (100, 'x', 1, '2025-10-01') RETURNING id;
 id
-----
 100
```

`ALWAYS` にしておくと、アプリのバグで ID を上書きしてしまう事故を防げます。

### ID には欠番ができる（実験で確認）

使い捨ての DB で次の順に操作しました。

1. NOT NULL 違反の INSERT が失敗 → エラーの `Failing row contains (2, x, 1, null)` から、**失敗した行に 2 番が割り当てられていた** ことが分かる
2. 次の INSERT（5 件）は **3 番から** 採番された（2 番は二度と使われない）
3. 行を DELETE した後の INSERT も、消した番号は再利用されず **続きの番号**（8）になった

理由: シーケンスの採番はトランザクションと無関係に進み、ROLLBACK や失敗でも **巻き戻らない** 仕様だからです（同時に複数の接続が INSERT しても番号がぶつからないための設計）。

- ただし、`VARCHAR` の長さ超過のように **値の変換の段階で失敗** したケースでは番号は消費されませんでした（採番より前にエラーになるため）。「失敗したら必ず欠番になる」わけでもありません。
- いずれにせよ **ID が連続している前提のコードは書かない** こと。「件数 = 最大 ID」は成り立ちません。

### 型は `BIGINT` で、JavaScript には文字列で届く

`BIGINT` は JavaScript の `number` で安全に表せる範囲（2^53 - 1）を超えうるため、`pg` は文字列で返します（→ 07 章）。backend の `parseInt(row.id)`（`backend/src/index.ts:57`）はこのためです。

## 今後に活かせるポイント

- 新しくテーブルを作るときは `id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY` を定番として使ってよい。
- 外部に見せる ID を推測されたくない場合は、連番ではなく UUID（`gen_random_uuid()`、`UUID` 型）を使う選択肢もある。
